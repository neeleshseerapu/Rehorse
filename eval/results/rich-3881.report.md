## Summary

_Written by the model at report time; everything else in this report is generated from recorded state._

On merge, prompt validation errors are styled instead of leaking their markup tags: with a Console(markup=False), Confirm.ask now shows a red "Please enter Y or N" rather than "[prompt.invalid]Please enter Y or N". The change is one line in rich/prompt.py — on_validate_error() now calls self.console.print(error, markup=True) — plus a CHANGELOG entry; there is no API change and no new argument. Verified by tests: all six acceptance criteria are covered by tests that failed before the fix and pass now (Prompt/Confirm/IntPrompt on a markup=False console, ANSI escape codes proving the markup is parsed rather than stripped, the existing markup-on tests unchanged, and Text messages still rendered verbatim), with the whole suite at 943 passed / 25 skipped against a 931-passing baseline. The independent verifier returned CONCERNS on the one behaviour this deliberately changes: because markup is now forced on, a str error message that echoes what the user typed is markup-parsed on a markup=False console, so "[hello] is not a valid choice" silently loses the bracketed text and an input of "[/]" raises rich.errors.MarkupError out of Prompt.ask entirely — the spec accepts bracket-parsing but did not anticipate an exception escaping the prompt loop. That crash path is a pre-existing hazard for markup=True consoles too, and the escape hatch is to raise InvalidResponse with a Text instance; if you would rather library code never widen it, the alternative is to render only the class-level default messages with Text.from_markup, which the spec considered and rejected.
