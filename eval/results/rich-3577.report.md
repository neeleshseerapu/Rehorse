## Summary

_Written by the model at report time; everything else in this report is generated from recorded state._

On merge, `Text.from_ansi()` keeps every line break its input contained: `Text.from_ansi("text\\n").plain` is now "text\\n" and `Text.from_ansi("\\n") == Text("\\n")`, closing rich#3577. The fix is a five-line change in `Text.from_ansi` plus a `_ends_with_line_break()` helper in rich/ansi.py that reuses `str.splitlines()` semantics, so \r\n still counts as one break and the exotic separators splitlines recognises (\v, \f, \x1c-\x1e, \x85, U+2028/9) behave as before; `AnsiDecoder.decode()` and `decode_line()` are untouched, so FileProxy and `python -m rich.ansi` gain no phantom blank line. Verified by 12 new tests plus 16 independent verifier tests, including spans on newline-terminated input (with and without a closing reset), multi-line styles, mixed terminators brute-forced over all strings up to length 4, and a FileProxy regression guard; full suite 981 passed, 0 failed. Two things to know before merging: this is a deliberate behaviour change, so anything decoding newline-terminated terminal output through `from_ansi` now renders one extra trailing blank line -- that is what required updating the expectations of the two pre-existing tests `tests/test_ansi.py::test_decode_issue_2688` (case 0) and `::test_decode_example`, which had pinned the buggy output, and it reaches `rich/pretty.py:316`, so a `__repr__` ending in a newline now renders with a trailing blank line. Nothing here was only eyeballed or type-checked; every claim above is covered by a test that ran.
